# 이메일 OTP 진입 인증 설계

## 목표

서비스의 첫 진입을 이메일 인증으로 바꾸고, 서버가 발급한 인증 세션이 유효한 경우에만 Frontend의 기존 메인 화면을 보여준다. 인증은 화면 진입용 게이트이며 회의·녹음 등 Backend 업무 API에서는 인증을 검사하지 않는다. DB나 Redis 없이 단일 Backend 프로세스의 메모리로 OTP 상태, 실패 잠금, 인증 세션을 관리한다.

## 사용자 흐름

1. 사용자가 이메일 주소를 입력하고 인증 메일 발송을 요청한다.
2. 서버는 이메일 형식을 확인하고 6자리 코드를 생성한다. 발송 성공한 코드만 서버에 등록하고 발송 후 60초 동안 유효하게 한다.
3. 화면은 코드 입력, 남은 유효 시간, 재발송 가능 여부를 표시한다. 사용자는 메일의 코드를 입력한다.
4. 서버는 이메일별 활성 challenge의 만료 시각과 코드 검증자를 비교한다. 성공한 코드는 한 번만 쓸 수 있다.
5. 틀린 코드가 다섯 번째 제출되면 해당 이메일의 새 코드 발급과 검증을 5분간 차단한다. 재발송은 실패 횟수를 초기화하지 않는다.
6. 인증 성공마다 서버는 UUID `sessionId`와 별도의 암호학적으로 안전한 세션 자격 증명을 생성한다. 자격 증명은 HttpOnly 쿠키로만 설정하고 `sessionId`는 현재 세션 식별자로 반환한다. 프론트엔드는 인증 상태를 다시 조회한 뒤 원래 요청한 화면으로 이동한다.
7. 브라우저는 실제 사용자 입력, 화면 이동, 업무 액션, 녹음 및 진행 중 작업을 활동으로 간주한다. 활동이 없는 2시간이 지나면 로그인 화면으로 돌아간다. Backend에는 세션 상태 확인과 활동 시각 갱신을 위한 인증 전용 endpoint만 두며, 기존 업무 API에는 인증 검사를 넣지 않는다.
8. 로그아웃 시 현재 브라우저 세션만 폐기하고 쿠키를 제거한다.

## 저장 및 만료 정책

- SQL DB, Redis, 브라우저 localStorage에는 OTP나 인증 토큰을 저장하지 않는다.
- 프로세스 메모리에서 이메일별 challenge, 실패 횟수/잠금 만료, 전송 쿨다운과 여러 동시 세션을 관리한다. 세션은 이메일을 키로 덮어쓰지 않고 각 인증마다 고유한 `sessionId`(UUID), `lastActivityAt`으로 구분한다. 정확한 idle TTL 비교는 주입 가능한 `Clock`을 사용한다.
- OTP는 `SecureRandom`으로 생성한다. 원문 코드를 보관하지 않고 서버 비밀 키를 이용한 HMAC 검증자만 저장하며 비교는 상수 시간 비교를 사용한다.
- challenge 발급 준비/활성화/교체/검증과 실패 횟수 증가는 이메일 단위로 원자 처리한다. 세션 생성/조회/폐기는 sessionId 또는 credential verifier 단위로 처리한다. 메일 발송에 성공한 뒤 challenge를 활성화하고 그 시점부터 60초 TTL을 계산한다.
- 동일 이메일은 60초마다 한 번만 발송할 수 있다. 발송 공급자 오류 시 인증 가능한 challenge를 남기지 않는다. 이메일별 제한은 Backend에서 강제하고 IP 제한은 신뢰된 proxy로부터 원 IP를 확인할 수 있을 때만 강제한다. 확인할 수 없으면 proxy 주소 전체를 하나로 묶어 사용자 발송을 막지 말고 운영 gateway에서 제한한다.
- 세션은 마지막 브라우저 활동 시각부터 2시간의 sliding idle TTL을 갖는다. 고정 절대 수명은 두지 않는다. 브라우저와 서버 모두 2시간을 관리한다. 쿠키 `Max-Age`도 활동 heartbeat가 성공할 때 7200초로 갱신한다. 세션 확인 조회는 활동으로 계산하지 않는다.
- 세션 쿠키는 `HttpOnly`, `Secure`(HTTPS 환경), `SameSite=Strict`로 제한하고 `Path`를 auth endpoint에만 적용한다. 개발에서는 `/api/v1/auth`, 운영에서는 Frontend가 사용하는 proxy prefix를 포함한 `/api/backend/api/v1/auth`로 `AUTH_COOKIE_PATH`를 설정한다. 이 경로 제한으로 회의·녹음 업무 API 요청에는 인증 쿠키를 보내지 않는다. 브라우저 저장소에는 인증 자격 증명을 넣지 않는다.
- `sessionId`는 세션을 식별하는 UUID일 뿐 인증 비밀이 아니다. 별도의 256-bit 무작위 bearer credential의 해시를 서버에 저장하고 원 credential만 HttpOnly 쿠키로 보낸다. 한 이메일로 여러 기기에서 인증해도 각 세션이 공존하며, 로그아웃은 현재 쿠키가 가리키는 세션 하나만 폐기한다.
- UUID는 실제 물리 기기를 식별하거나 브라우저 지문을 만드는 값이 아니라 인증 세션 ID다. 같은 쿠키를 공유하는 탭은 같은 세션으로 취급한다. 다른 기기의 세션 목록/원격 로그아웃 UI는 이번 범위에 포함하지 않는다.
- 프로세스 재시작 시 OTP, 잠금, 쿨다운, 세션 모두 사라지고 기존 쿠키는 무효가 된다. 여러 Backend 인스턴스는 지원하지 않는다. 운영 배포는 단일 인스턴스여야 한다.
- OTP HMAC 키와 세션 cookie의 Secure 플래그는 `OTP_HMAC_SECRET`, `AUTH_COOKIE_SECURE`로 Backend 환경에서 설정한다. HTTPS proxy 뒤에서는 Backend가 내부 HTTP로 요청을 받더라도 운영 환경에서 `AUTH_COOKIE_SECURE=true`를 명시한다.

## 메일 발송

기존 Backend에는 Gmail API OAuth2 메일 어댑터와 server-side 환경 설정이 있다. 인증 코드는 회의록 메일과 구분된 깔끔한 HTML 템플릿과 plain-text 대체 본문으로 발송하며 기존 `EMAIL_*` 서버 환경 변수의 Gmail API credentials/sender를 재사용한다. Frontend 이메일 알림 설정이나 브라우저 설정 복구에는 의존하지 않는다. 메일 미설정이나 발송 실패를 화면에서 안내하고 OTP 값, 전체 이메일, 제공자 응답 본문은 로그에 남기지 않는다. 운영 환경에 발송 권한과 발신 주소가 준비되어야 인증 진입이 가능하다.

## 접근 정책 가정

제품에 사용자/허용 목록이 정의되어 있지 않으므로, 초기 범위에서는 유효한 이메일 주소의 소유를 증명한 누구나 접근할 수 있다고 가정한다. OTP는 이메일 소유 확인이며 사용자를 사전 등록하거나 역할을 부여하는 수단은 아니다. 사용자 또는 도메인 allowlist가 필요하면 별도 요구사항으로 이 정책을 바꿔야 한다.

## 보호 경계

- Frontend는 모든 URL을 인증 화면으로 가드하고 인증 성공 후 요청한 내부 경로로 돌아간다. 유휴 2시간이 되면 열린 URL과 무관하게 메인 화면을 닫고 인증 화면으로 보낸다.
- Backend 인증 endpoint는 `/api/v1/auth/**` 아래 상태 확인과 활동 갱신만 제공한다. 기존 회의·녹음·문서 업무 API에는 인증 cookie 검사, 401 가드, interceptor/filter를 추가하지 않는다.
- `GET /api/v1/auth/session`은 현재 session과 idle 만료까지 남은 시간을 확인하며 last activity를 변경하지 않는다. `POST /api/v1/auth/session/activity`만 유효 세션의 `lastActivityAt`을 갱신하고 cookie 만료를 연장한다. 만료 세션은 인증 화면이 표시될 수 있도록 미인증 결과를 반환한다.
- activity endpoint의 CORS/Origin 정책은 인증 상태 갱신 범위에서만 적용한다. 업무 API의 현재 접근 방식은 변경하지 않는다.
- 이메일은 trim 후 소문자 기준으로 정규화한다. 인증 endpoint 응답은 코드 발송 성공 여부 외에 계정 존재 여부를 드러내지 않는다.

## 사용자 화면

현재 제품 헤더와 모바일 레이아웃을 재사용하는 인증 진입 화면을 만든다. 초기 단계에서는 이메일 입력과 메일 발송 버튼을, 발송 후에는 6자리 OTP 입력, 60초 만료 카운트다운, 재발송 상태를 보여준다. 입력 오류, 만료, 발송 실패, 5회 실패 잠금은 서버 응답에 맞는 한국어 안내로 표시한다. 키보드/붙여넣기, 모바일 숫자 키패드, 로딩 중 중복 제출 방지를 포함한다.

## 대안 및 선택

- **프로세스 메모리(선택)**: 현재 무 DB 단일 서버 구조에 가장 적합하고 TTL 구현이 단순하다. 재시작 및 수평 확장에 취약하므로 단일 인스턴스 제약을 운영 계약으로 둔다.
- **Redis**: 인스턴스 간 상태 및 재시작 유지가 필요할 때 적합하지만 새 인프라와 운영비가 필요하다.
- **암호화 파일**: 추가 서비스는 없지만 동시성/원자성/만료 청소를 애플리케이션이 떠안으며 현재 세션 처리 구조와 맞지 않아 선택하지 않는다.

## 완료 조건

- 메일 발송만으로는 진입할 수 없고, 만료 전 올바른 코드를 서버가 확인한 후에만 인증 세션이 발급된다.
- challenge의 만료, 1회 사용, 5회 실패 잠금 5분, 재발송 후 실패 횟수 유지, 세션 만료/로그아웃이 backend 테스트로 검증된다.
- 브라우저 유휴 2시간이 지나면 인증 화면으로 돌아가고, 화면 이동·사용자 액션·녹음·활성 처리 작업은 idle 기준을 갱신한다.
- 인증 상태 endpoint만 세션을 확인/갱신하며, 회의·녹음 등 Backend 업무 API에는 인증 검사가 추가되지 않는다.
- 새 DB/Redis는 사용하지 않는다. 배포 환경의 Gmail 설정 및 단일 인스턴스 조건을 별도 운영 점검한다.

## 미결 정책 위험

허용 목록이 없으면 이메일 소유자는 모두 서비스에 들어올 수 있다. 서비스가 조직 전용이어야 한다면 allowlist 또는 회사 도메인 제한을 구현 전에 요구사항으로 확정해야 한다. 프로세스 메모리 기반 구현은 단일 인스턴스·재시작 시 재로그인 필요 조건을 전제로 한다.
